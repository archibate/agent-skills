# Private X11 with Xvfb and Openbox

Use installed tools and their local help to build a small task-specific launcher.
The aim is a managed private session, not a universal launcher or fixed display
number. Check availability of `Xvfb`, `openbox`, `xdotool`, and a capture utility
such as ImageMagick `import`; use suitable equivalents when available.

## Launch and ownership

- Create a uniquely named private scratch directory. Put session metadata, logs,
  application test data, screenshots, and curated configs there.
- Start Xvfb with `-displayfd` connected to a launcher-owned pipe, a fixed screen
  size/depth, and `-nolisten tcp`. Read the allocated display number; do not assume
  `:2` or `:99` is free or owned. Configure and verify local X access restrictions
  (for example, a private Xauthority cookie); `-nolisten tcp` only closes TCP.
  Do not weaken access controls with `xhost +` or `-ac`.
- Record child process identities and lifecycle handles. Wait with a deadline for
  the server to become ready. Cleanup must also handle partially failed startup.
- Build a scoped child environment with explicit private `DISPLAY`, relevant
  `XAUTHORITY`, and private HOME/XDG config, data, cache, and runtime paths. Unset
  inherited `WAYLAND_DISPLAY` and shared session-bus endpoints that could route
  clients to the live desktop. Retain only needed runtime/provider variables;
  do not dump credentials into logs. Verify the actual app's routing and paths.
- Launch `openbox` directly with a private minimal config, rather than a full
  desktop autostart session. Set predictable geometry, focus behavior, and a dark
  theme if available. Avoid inherited autostarts, notification agents, global
  shortcuts, and desktop services. If an app needs D-Bus, create a private bus.
- Launch the application in that environment with an isolated profile/data root
  and verified silent output. Wine applications may need a separate prefix;
  single-instance apps may need an explicit new-instance option. Verify effective
  save/config paths and cloud-sync behavior before letting the app write.

Xvfb isolates display/input routing, not network or filesystem access. Use verified
application controls or a permitted OS isolation mechanism for offline execution;
do not label an ordinary Xvfb launch an offline sandbox.

## Capture and events

Run every command below through the same private environment. These are building
blocks to adapt after ownership and routing checks, not commands for the inherited
default desktop.

| Need | Building block |
|---|---|
| Capture desktop | `import -window root <unique-frame.png>` |
| Find application window | `xdotool search --onlyvisible --name <pattern>` |
| Inspect geometry | `xdotool getwindowgeometry --shell <window-id>` |
| Focus window | `xdotool windowactivate --sync <window-id>` |
| Check focus | `xdotool getwindowfocus` |
| Move in root coordinates | `xdotool mousemove <x> <y>` |
| Move relative to window | `xdotool mousemove --window <window-id> <x> <y>` |
| Click / scroll | `xdotool click <button>`; wheel buttons are 4/5 |
| Hold / release | `xdotool keydown <key>` / `keyup <key>` |
| Drag | `mousedown 1`, ordered movement, then `mouseup 1` |
| Type text | `xdotool type --clearmodifiers --delay <ms> -- <text>` |

Resolve ambiguous window matches using owned process/window evidence before input.
Validate focus against the expected window or its actual focused child. Put a
timeout around readiness/focus operations so a missing window cannot hang the run.
Some games require keydown/keyup separated by several frames; observe the actual
effect and tune the hold duration. Focused XTEST input may work where synthetic
events sent directly to a window are ignored. Quote text as data rather than shell
code; clipboard use must stay within the private session.

Keep capture resolution stable. Root screenshots naturally pair with root input
coordinates. If an image reader resizes a capture, map its coordinates back to
native pixels. A cropped window capture needs its root origin added; account for
decorations and client-area offsets rather than guessing.

Write each capture to a fresh path, check capture success, and read that exact file
as an image. Do not let a failed capture reuse an older successful frame. Root
captures may omit the hardware pointer: distinguish screenshot limitations from
an application failing to draw its cursor.

## Bounded lifecycle

Keep stdout/stderr, action checkpoints, and final screenshots in the scratchpad.
Use `finally`/traps to release held input while the owned display still exists,
then stop the owned app, window manager, bus if created, and X server. Prefer live
child handles; for persisted PIDs, verify process start identity before signalling
to avoid PID reuse. Never reclaim an occupied display or kill another session to
make the launcher work. Retain diagnostic files on failure and report their paths.
